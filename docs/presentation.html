01 · Problem Statement

Why manual library handling doesn't scale

Manual tracking breaks down

  • Records live in ledgers or spreadsheets — easy to duplicate or lose.
  • Borrowing state becomes inconsistent: two people for one copy, or an unreturned book nobody tracks.
  • Answering simple questions — what's available? who holds this book? — takes too long.
  • No reliable history, no single source of truth.

What this system solves

  • One consistent catalog of books and members.
  • Enforced borrowing rules (limits, uniqueness, availability).
  • Fast search and sort across the whole catalog.
  • Persistent storage, so state survives restarts.
  • A clean, layered design that stays maintainable as it grows.
02 · Project Objectives

What the project sets out to do

  • Manage books and members — add, remove, list, and inspect records.
  • Support borrowing and returning — with enforced limits and availability rules.
  • Search and sort the catalog — flexibly, by multiple fields and algorithms.
  • Keep data organized and consistent — invariants hold after every operation.
  • Provide a clean, maintainable design — separated layers, tested behavior, no leaks.
Say: "These five objectives map directly onto the layers I'll show next — each goal is owned by exactly one part of the design."

How data flows

1. User acts through the interface
2. Request reaches the service layer
3. Business rules are checked
4. State changes in memory and is written to storage

Each layer depends only on the one beneath it, so an internal change stays local.

Say: "Follow the arrow — a user action goes into the UI, is handled by the service, and only the service touches storage. No layer reaches over another."
04 · Architecture

Separation of concerns

UI layer

Handles user interaction only: menus, input validation, and formatted output. It never contains business rules.

Service layer

The single entry point for all operations. Owns the business logic and protects the system's invariants.

Domain layer

Contains the entities and their rules — Book and Member — which validate themselves and cannot exist in an invalid state.

Core layer

Holds the reusable data structure (Container<T>) that stores the catalog and borrowed lists.

Repository layer

Handles persistence behind an interface. The rest of the system never talks to SQLite directly — it only sees ILibraryRepository.

Why it matters: a change in storage, or a new search option, touches one layer — not the whole program.

06 · Custom Data Structure

Container<T> — a custom doubly linked list

Why build it instead of using std::list?

  • The core exercises data-structure internals directly — not a black box.
  • Full control over memory, iterators and sorting.
  • Proves the algorithms the project relies on, from the ground up.

Properties

  • O(1) insert/remove at both ends (head & tail pointers).
  • Stable node references — pointers survive sorting and relinking.
  • Bidirectional iterators with a documented traversal model.
  • Stable in-place merge sort and insertion sort that relink nodes instead of copying data.
  • Exception-safe: operations leave the container valid on failure.

Role in the project: it stores the book catalog and every member's borrowed list, and powers search, sorting and the stress tests.

Say: "The important guarantee is stability — sorting relinks the nodes instead of copying data, so references to a book stay valid after a sort."
07 · Design Patterns

Patterns chosen where they add real value

Facade — LibraryService

One simple entry point that hides the container, the strategies and the domain rules behind a small, stable API.

Strategy — search & sort

ISearchStrategy and ISortStrategy let the system swap the search field, sort key and algorithm without changing the service.

Repository — storage

ILibraryRepository abstracts persistence, so the same logic runs against SQLite or an in-memory store.

Command — menu actions

Each menu entry wraps an action, keeping the UI loop small and keeping navigation data-driven.

Result: new behavior is added by extending — not by rewriting existing code.

08 · Domain Model

Entities that guard their own correctness

Book

Fields: title, author, ISBN, genre, availability.

  • Text fields are trimmed and non-empty.
  • ISBN is normalized and validated (10 or 13 characters).
  • Identity is the ISBN — so ISBNs stay unique.
  • Availability can only flip through mark_borrowed / mark_returned.

Member

Fields: id, name, list of borrowed ISBNs.

  • id > 0, name non-empty.
  • At most 5 borrowed books at a time.
  • No duplicate ISBNs in the borrowed list.
  • Identity is the id.

Because constructors and setters validate first, no invalid object can be created — and the service keeps the bigger invariants (uniqueness, borrow rules) true after every call.

09 · Database & Persistence

SQLite behind a repository abstraction

  • SQLite backend (bundled, no external dependency).
  • ILibraryRepository defines storage; SqliteRepository implements it.
  • An in-memory repository keeps the app usable without a database.
  • Availability is not stored — a book is borrowed exactly when it has an open loan (single source of truth).

Write-ahead ordering

1
Validate everythingall checks happen first
2
Write to the databaseif it fails, memory is untouched
3
Update in-memory stateconsistency is preserved

Separating logic from the database means the business rules stay storage-agnostic — easy to test, and easy to replace or extend.

Say: "Availability is derived from open loans, not stored twice — that removes a whole class of bugs where the book and the loan disagree."

11 · Example Workflow

Borrowing a book, step by step

1
User chooses “Borrow book” from the UIThe menu entry triggers the borrow action.
2
InputReader reads the ISBN and member idThe ISBN format and the id range are validated immediately.
3
LibraryService applies the business rulesNormalizes the ISBN; finds the member and book; checks availability and the 5-book limit.
4
The repository records the loanSqliteRepository inserts an open loan — the durable source of truth.
5
In-memory state is updatedThe book is marked borrowed and the ISBN is added to the member's list.
6
The UI reflects the new stateThe updated catalog is shown as a formatted table.

If any rule fails, the operation throws a typed error and nothing changes — the same input can be retried safely.

Say: "This is the whole project in one slide — validation first, then the database write, then memory last. That order is what gives us the strong exception guarantee."
